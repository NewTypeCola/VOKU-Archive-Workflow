# 3. 검수 결과가 다음 판독과 도구의 입력이 되었습니다

[English](../../../history/cases/03-review-and-repair.md)

[History](../HISTORY.md) · [후속 합성](05-composition.md)

1차 이름 처리에서 남은 partial/hold 4,287쪽은 같은 종류의 실패가 아니었습니다. 기계 문제만 2,768쪽, 의미 문제만 1,087쪽, 둘 다 426쪽, 빈 OCR 6쪽이었습니다. 한 회차에 한 장만 보류로 남은 경우도 918개 있었습니다. 이미 얻은 신원 판단을 다시 하는 것과, 그 판단을 실제 픽셀에 적용하는 데 실패한 영역을 고치는 것은 다른 작업이었습니다. [E12](../reference/evidence.md#e12)

## 독립 재작업으로 갈라진 직접적인 이유

9월 10일 사용자는 기존 패키지가 “1차용 빠르게 훑기 용”이며 재작업용으로 설계된 것이 아니라고 정정했습니다. 기존 CLI·큐·편성 임대를 재사용하는 설계 대신, 기존 결과를 자료원으로 삼는 별도 실행 구조를 요구했습니다. 이때의 요청은 계획까지만이었고, 설계 과정에서 생산을 시작하지 않았습니다. 실제 구현은 뒤의 개별 작업들에서 이뤄졌습니다. [E30](../reference/evidence.md#e30)

운영 제약도 구체적이었습니다. 의미 판독 큐가 소진된 두 세션으로 과거 보류를 열면 연도 소유권 검사 `REVIEW_OUTSIDE_SESSION_YEAR`에 막혔습니다. 또한 완료본을 보고 사람이 issue로 표시한 페이지는 당시 hold/partial 페이지와 겹치지 않았습니다. 전자는 이전 결과를 보존하면서 교체본을 만들어야 하고, 후자는 아직 정상 결과가 없는 쟁점을 해결해야 했습니다. 같은 재시도 명령에 넣기 어려운 서로 다른 입력이었습니다.

따라서 이후의 분기는 폴더를 보기 좋게 나눈 결과가 아닙니다. **기존 완료본의 오류, 원래 보류, 새로 발견한 누락, 특정 이름의 기하 보정**이 서로 다른 입력 상태와 보존 요구를 가졌기 때문입니다. 초기와 후기 연도는 대상 규모·신원 문맥·사용자 검토 범위도 달랐습니다. 다음 표의 분모들은 서로 다르며 일부 후속 대상은 겹칩니다.

## 사람 검토를 저장하고 다시 읽는 방법도 바뀌었습니다

일반 앱은 실제 출력 21,009쪽을 보여주고 현재 ok 17,042 / issue 321 / needs_review 3,646을 기록합니다. 별도 hold 앱은 보류 **원본**을 보여줍니다. 초기 2,057쪽과 후속 지정 9쪽을 연결 해제한 뒤 활성 2,221쪽은 모두 미검토입니다. 같은 페이지 위치를 말하더라도 출력 기준 bbox와 원본 기준 bbox를 구별해야 했습니다. [E14](../reference/evidence.md#e14)

처음의 메모 중심 검수에 bbox 입력이 붙었고, 한글 IME에서 Enter가 뜻하지 않게 제출되는 문제와 초안 보존이 보완됐습니다. bbox의 이름 칸에 마스크 오류 설명이 들어가는 경우도 있었습니다. 이 필드를 곧바로 인명 원장으로 쓰지 않고, 다음 에이전트가 확인할 문제 안내로 소비했습니다. 이미지 fingerprint가 바뀌면 옛 의견은 이력으로 남고 현재 버전은 다시 검토 대상이 됐습니다. [좌표 코드](../../../history/historical/review/geometry.js)

9월 14일 별도 후기 이름 보정 패키지는 이 사람 기록을 잘못 읽었습니다. 메모·박스가 있거나 `issue`인 항목만 모아 미해소 문제를 3쪽으로 셌습니다. 그러나 실제 앱의 Space 저장은 내용 없는 `needs_review`와 NULL fingerprint를 남길 수 있었습니다. 그것도 사용자가 남긴 표시였습니다. 저장 이력을 시간순으로 재생해 이후의 유효한 `saved ok`만 해소로 인정하자 대상이 1,805쪽으로 늘었습니다. 자동 `source_changed`도 수동 표시를 해소하는 이벤트가 아니었습니다. 후보가 하나도 없던 4쪽까지 포함됐고, 기계 후보 목록에 이미 있던 페이지도 별도의 검수 의무를 되찾았습니다. [E31](../reference/evidence.md#e31)

## 이미 아는 사람의 짧은 호칭: 신원은 유지하고 경계만 다시 풉니다

한 회차 28쪽의 저장 OCR에서 두 인물의 두 글자 호칭 10곳을 확인했습니다. 8쪽은 이전 `no_changes`였습니다. 첫 적용은 9곳·8쪽까지였고 한 곳은 호칭 경계에서 막혔습니다. 떨어진 모음 획을 다음 호칭의 시작으로 나누는 문제가 있어, 실측 잉크 폭과 빈 열 경계를 보완한 뒤 10곳·9쪽으로 마쳤습니다. [E15](../reference/evidence.md#e15), [원래 보정 함수](../../../history/historical/names/short_alias.py)

이때 다음 단계가 받은 것은 새 신원이 아니라 **이미 확정한 인물 연결과 아직 실패한 기하**였습니다. 전체 OCR을 다시 만들지 않고 동일 후보를 재사용해 좌표와 결과만 검증했습니다. 나중의 다른 호칭 보정도 초기의 보존 정책을 무조건 누락으로 간주하지 않고, 해당 시점의 새 처리 지시를 따랐습니다.

## 보류 복원에서 캐시와 합성의 문제가 드러납니다

후기 보류 첫 패키지는 같은 회차의 기존 처리와 미해결 부분을 함께 다뤘습니다. 한 영역을 원본으로 복원하는 일이 같은 페이지의 다른 새 마스크를 되살릴 수 있었습니다. 검증을 개별 연산에서 끝내지 않고, 최종으로 합성된 페이지에서 기존·새 대상과 보호 픽셀을 함께 확인하도록 바꿨습니다. [render contract](../../../history/historical/repair/render_contract.py)

캐시도 단순한 성공/실패 저장으로 부족했습니다. 이름 범위가 바뀌었는데 이전 성공을 재사용하는 문제는 입력과 범위에 연결된 유효성 검사가 필요했습니다. 반대로 신원 연결만 바뀌었을 때 유효한 좌표까지 버리는 문제는 물리적 등장 위치와 출력 신원을 분리해야 했습니다. deferred 제출이 중간에 실패한 경우에는 남아 있는 상태에서 마무리하는 경로를 보완했습니다. [E17](../reference/evidence.md#e17)

현재 DB의 artifact 이력은 58행이지만 고유 페이지는 18쪽이며, 새 물리 출력은 15개입니다. 이 경로는 여러 오류를 고쳤으나 후기 2,230쪽 전체 완료에 도달하지 않았습니다. 뒤의 합성은 이 경로의 존재하는 결과만 상위 수정 레이어로 받을 수 있었고, 전체 후기 보류를 채우는 일은 별도 경로에서 이뤄졌습니다.

## 후기 이름 누락 보정: 과거 마스크 기록도 입력 형식이었습니다

검수 선정 오류를 고친 계획 패키지는 후기 이름 누락 보정 경로 (`voku-name-repair`)로 옮겨졌습니다. 사용자는 반복 탐색과 이미지 우선 판독을 줄이고 저장 OCR 판단→코드 보정→이미지 예외 순서를 원했습니다. 기존 신원·회차별 연결·마스크를 유지하면서 누락 표기와 새 문맥만 판단하도록 구성했습니다. 이 경로의 대상은 후기 보류 2,230쪽에만 한정되지 않았습니다.

실제 렌더 중에는 `token_layout=null`인 과거 영수증에서 `.get('box')`를 호출해 멈췄습니다. 이름은 이미 지워졌으나 토큰을 넣지 못한 기록이었습니다. null을 “기존 마스크 없음”으로 읽으면 과거에 보호한 영역을 잃습니다. 명시적 `token_rendered=false`, 삭제 영역, 같은 등장에 연결된 geometry를 함께 읽고, 근거가 부족할 때만 구체적인 보류로 남기도록 고쳤습니다. 당시 동결 입력에서는 null 레이아웃 1,652항목이 975쪽에 있었습니다.

시험 중에는 복사된 표시 대응표의 절대경로가 원래 출력 한 개를 가리켜, 시험용 정리 코드가 실제 표시 파일을 지우는 사고도 있었습니다. 불변 백업에서 같은 해시로 복구한 뒤 표시 경로를 시험 사본과 분리하고 보존 검사를 추가했습니다. 이 사건은 “격리 폴더에서 실행했다”는 조건만으로 모든 참조가 격리되는 것은 아니라는 실제 수정으로 남았습니다.

그 뒤 생산을 재개해 51/457편성을 처리하고 사용자의 중단 요청에 멈췄습니다. 당시 보고는 OCR 대조 52편성·4,401쪽, 처리 범위 51편성·4,275쪽, 출력 279쪽과 기존 수동 검수 1,805쪽 보존을 기록합니다. 현재 출력 279개는 존재하지만 해당 production 상태 디렉터리의 실행 파일들은 남아 있지 않습니다. 따라서 진행 수는 당시 STOP 기록과 memory, 출력 수는 현재 물리 파일로 구분해 근거를 남깁니다. 최종 합성으로의 반영 연결은 확인되지 않았습니다. [E31](../reference/evidence.md#e31)

## 같은 후기 보류를 다시 다룬 해소 경로 (new-boryu)

별도 `new-boryu`의 처음 2000년 엔진은 매 페이지 실제 이미지 확인을 요구했습니다. 사용자는 빠른 OCR 중심 1차 처리 뒤 본인이 최종 육안 검토를 하겠다고 정정했습니다. 2001년 이후에는 보류 페이지의 저장 OCR을 읽는 연속 처리기로 바뀌었습니다. 회차 문맥 전체를 매번 반복하는 대신 이번 작업에서 필요한 held_pages를 읽도록 범위도 정했습니다. [E18](../reference/evidence.md#e18)

2000년 195쪽과 2001–2019년 2,035쪽이 각각 독립 완료됐습니다. 질문 2,835개가 resolved라는 수치에는 기계 기하 해결 2,364개가 포함돼 있어, 사람이 2,835번 답했다는 뜻이 아닙니다. 에이전트 이미지 확인 표시, 기술 검증, `human_approved=false`, 원천 hold 상태는 각각 남았습니다. 로컬 결과는 이후 합성의 이름 레이어로 소비됐으며 원천 DB를 강제 완료로 바꾸는 절차는 아니었습니다.

## 검토 결과를 새로운 수정 범위로 돌려보냅니다

supplement의 최초 needs_review 3,646쪽에는 bbox·메모가 없었습니다. 에이전트가 저장 OCR에서 문제를 찾아야 했고, 뒤에 issue 106쪽과 새 bbox 대상 197쪽이 더해져 현재 3,949쪽이 됐습니다. 3,800쪽은 로컬 완료, 149쪽은 변경 없음입니다. 별도 후기 검토 앱의 76/200/78건 export는 다음 보정 패키지의 입력 snapshot과 연결됩니다. [E19](../reference/evidence.md#e19)

최종 합성 뒤에는 이름 누락 감사 (`tri-force-gumsu`)가 결재란 처리 12,194쪽을 이름 감사의 표본 범위로 사용했습니다. 이름 레이어가 없던 554쪽을 곧바로 누락이라고 세지 않고, OCR 후보·현재 픽셀·기존 대상·문맥을 대조했습니다. 저장된 최종 조사에서 누락 확인은 1,137쪽이었습니다. 확인된 이름들이 기존 유효 대상 목록에도 빠져 있어, 조사 보고는 합성 전달 손실보다는 앞 단계 이름 선택을 다시 볼 근거를 남겼습니다. [E32](../reference/evidence.md#e32)

270쪽·436개 기하 후보 초안은 렌더·등록 전에 중단됐습니다. 이후 이미 완료한 106쪽을 제외하면서 겹치는 41쪽을 빼 가이드 대상은 229쪽이 됐습니다. 사용자가 지정한 25쪽과 추가 3쪽을 제외한 201쪽에는 별도 확정한 394연산이 적용됐습니다. bbox는 문제를 찾으라는 안내에서 최종 지움 영역으로 한 번 더 해석됐습니다. 가상배역, 취소된 이름, 한 글자 화자, 표 선 접촉, 마스크 여유 폭에 대한 시점별 사용자 결정도 이 후속 입력에 포함됐습니다.
