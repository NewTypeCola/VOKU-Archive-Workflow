# 6. 최신 영수증 밖에 있던 토큰과 이미지 뒤의 OCR

## 완료라고 보고했는데 8개가 그대로였습니다

토큰 타이포그래피 수정 뒤 사용자가 한 페이지의 누락 이유부터 물었습니다. 조사 결과 최신 수정 기록에 있는 제작진 토큰은 바뀌었지만 후기 이름 보정 경로 (supplement)의 이전 수정에서 이미 합성된 8개 토큰은 목록에 들어가지 않았습니다. 백업과 해당 영역의 픽셀이 같아 실제 미수정임을 확인했습니다. 원인은 **최신 영수증만 읽고 이전 revision을 재생하지 않은 준비 로직**이었습니다. [E25](../reference/evidence.md#e25)

그 후 사용자는 한 페이지의 해당 8개만 2+2글자·13px로 바꾸고 기존 4글자 토큰은 건드리지 않도록 지정했습니다. 과거 glyph를 정확히 재생해 제거한 뒤 새 토큰을 그렸고, 비대상 영역과 다른 66,009쪽을 보존했습니다. 이는 새 판단이나 후보 재탐색이 아니라 정해진 역사적 연산을 추적한 제한 보정입니다.

다른 타이포그래피 경로에서도 오래된 private 보호가 최신 토큰 영역을 막는 문제가 있었습니다. 보호 마스크들을 무조건 합집합하는 것만으로는 이벤트 순서를 표현할 수 없었습니다. landscape·제작진·portrait 배치가 서로 다른 기준을 쓰고 사용자가 크기와 예외를 정했기 때문에 한 전역 글꼴 크기로 단순화하지 않았습니다.

## 정확한 bbox 밖에 남은 획은 별도의 판단이었습니다

후속 staff 15쪽 수정은 26개 입력 영역에 대해 새 토큰 21, 마스크만 3, 수평 이동 2를 처리했습니다. 사용자는 **입력한 bbox만 정확히 적용**하도록 지정했습니다. 박스 밖의 잔획을 자동으로 넓혀 가리지 않았고, 허용 영역 밖 변경 0이라는 검증을 남겼습니다. 이런 잔존을 도구가 임의로 ‘미완료’라고 판정해 범위를 넓히면 사용자 결정을 훼손합니다. [E25](../reference/evidence.md#e25)

## 원본 OCR 치환 계획에서 최종 이미지 새 OCR로

초기 OCR 민감 표기 치환 계획 (P0-5A)에는 원본 OCR의 민감 표기를 치환하는 구상이 있었습니다. 8월 21일 수정안은 공개용 텍스트가 최종 이미지와 맞아야 하므로 최종 WebP를 다시 OCR하고 옛 OCR은 매핑·QA 근거로 쓰도록 바꿨습니다. 당시 입력 자료 폴더 (`game`)에 전체 실행이 없다는 관측과 이후 최종 합성·OCR 작업 폴더 (`final-tri-force`)에 실제 전체 OCR이 있다는 관측은 모순이 아닙니다. **계획과 후속 실행 사이의 연결**입니다. [E02, E24](../reference/evidence.md#e24)

두 번의 전체 생성 기록은 각각 66,010쪽·5,330문서이며 첫 결과 1,990,913줄, 다음 결과 1,992,139줄입니다. 그 사이 최종 이미지 21,314쪽이 달라졌다는 비교가 있습니다. 이 수치를 서로 겹치는 교정 배치 수의 합으로 만들지 않습니다. [실제 Swift OCR 코드](../../../history/historical/ocr/vision_ocr_multiprocess.swift)

이후 이름 62쪽과 연락처 52쪽의 지정 보정에 맞춰 각각 39개 회차 JSON을 갱신했습니다. 같은 JSON의 비대상 페이지 객체 633개와 447개를 각각 보존하고, 매번 나머지 5,291개 JSON을 보존했습니다. 현재 직접 재집계한 결과는 1,992,165줄입니다.

## 검증 실패를 출력 실패로 오해하지 않기

Python과 Swift가 macOS 파일명의 Unicode 정규화를 다르게 다뤄 경로 비교 검증이 실패했습니다. 파일을 다시 이름 바꾸거나 전부 OCR하지 않고 정규화와 `samefile` 대조를 보완했습니다. 원본 빈 페이지 7쪽은 사용자 확인 후 설명을 남겼고, 정규화 bbox가 경계를 조금 넘는 15줄/13쪽은 원값을 보존했습니다. 좌표를 조용히 clamp하지 않았습니다. [E24](../reference/evidence.md#e24)

현재 이미지, 과거 최상위 manifest, 후속 영수증, OCR의 `sourceSHA256`은 다른 시점을 가리킬 수 있습니다. 오래된 manifest 표본의 불일치는 후속 백업·적용 영수증·현 이미지/OCR 해시로 설명됩니다. [E26](../reference/evidence.md#e26)

최종 상태는 하나의 `done=true`가 아니라 현재 이미지 집합, 그 이미지에서 생성한 OCR, 국소 교정 영수증, 검토 상태가 서로 연결된 결과로 남았습니다.
