# 2. 작업자를 바꾸는 것에서 판독 단위와 인계를 바꾸는 것으로

[English](../../../history/cases/02-reading-and-state.md)

[History](../HISTORY.md) · [관련 추가 근거](../reference/evidence.md#e27)

9월 초의 이름 처리는 하나의 엔진을 순서대로 업그레이드한 이력이 아닙니다. 이미지 작업자, 저장 OCR만 쓰는 별도 경로, 주 처리의 격리 기하 시험, 단일 에이전트 대체본, 세션 대체본이 겹쳐 있었습니다. 결과와 결정이 실제로 넘어간 연결을 따라가면, 어떤 변화가 에이전트 수의 변경이었고 어떤 변화가 판단·좌표·작업 범위의 변경이었는지 구별할 수 있습니다.

## 이미지 작업자 운영에서 남은 문제

이미지 작업자 기반 이름 처리 (`voku-ocr-v3`)에서는 메인이 OCR과 routing을 맡고 실제 이미지 작업자가 원본 확인·bbox·마스크·결과 검토를 수행했습니다. 9월 5일 중단 기록의 172문서·2,170쪽과 별도로, 지정 모델을 시험한 세 회차 작업은 claim 뒤 사용자가 즉시 중단시켜 적용 전 상태에 남았습니다. 중단할 때 새로 생긴 토큰과 부분 작업은 지우지 않고 보존했습니다. [E10](../reference/evidence.md#e10)

선별 오버레이 처리 (overlay) 경로는 읽을 자료를 작게 만드는 쪽을 시험했습니다. 짧은 단독 제작진과 손상된 소개 줄이 compact 선별에서 빠져 선별 규칙을 보완했습니다. 사용량 중단으로 남은 작업은 새 위치에서 기존 자료를 받아 계속했습니다. 첫 55쪽과 후속 896쪽은 서로 다른 실행 범위입니다. 완료본을 취합할 때는 6,920쪽 중 승인 연결이 빠진 67건을 과거 review reply·열람·geometry 근거에서 복구했고, 사용자가 저장 위치를 정정하자 이미지를 다시 만들지 않고 경로를 옮겨 연결을 고쳤습니다.

이미지 작업자 운영 (Luna v3)은 최대 세 작업자가 여섯 쪽씩 맡는 방식으로 실제 재개됐습니다. 여기서는 한 작업자의 완료 보고와 실제 서명·날짜 겹침 및 렌더 제한 결과가 맞지 않았습니다. 완료 숫자를 그대로 수집하지 않고 해당 결과를 hold로 되돌렸습니다. 활성 작업까지 마친 중단 집계는 13쪽 중 12 masked·1 hold, 미수집·활성 작업 0이었습니다. 에이전트의 보고도 실제 영수증·출력과 대조할 대상이었습니다. [E33](../reference/evidence.md#e33)

## 같은 시기 존재했던 다른 타협: OCR 줄 전체 재기입

OCR 읽기 전용 실험 (`voku-ocr-readonly`)은 새 OCR과 에이전트 이미지 열람을 금지하고 저장된 좌표만 사용했습니다. 정밀한 기존 마스크 bbox가 없으면 저장 OCR의 줄 전체를 덮고, 이름을 토큰으로 바꾼 문자열을 다시 그렸습니다. 주변 **문자열**은 유지하지만 원래 필체·서체·간격과 OCR 오탈자를 그대로 보존하는 방식은 아니었습니다. 이 제약은 당시 README와 코드에 명시돼 있습니다.

9월 5일의 현재 영수증은 59회차·644쪽을 가리키며, 출력 210쪽과 `saved_ocr_line_bbox` 적용 538건이 남아 있습니다. 진행 요약은 그보다 이른 40회차·485쪽·153출력에서 멈췄습니다. 따라서 이 경로의 실행 범위는 요약 하나보다 영수증과 실제 파일을 함께 읽어야 합니다. 이 별도 결과가 주 처리로 이관됐다는 연결은 발견되지 않았습니다. [E34](../reference/evidence.md#e34)

## 52쪽 시험 뒤에 실제로 이어진 기하 수리

주 처리의 격리 시험은 4문서·52쪽에서 verified 12 / no_changes 30 / partial 8 / hold 2로 끝났습니다. 네 문서 모두 보류였고 export는 0이었습니다. 이름을 읽고 결정문을 만드는 데 약 310초, geometry와 render 서비스 합계는 약 17초였지만, 이 표본에서 당장 막힌 문제에는 좌표와 토큰 배치도 있었습니다. [E11](../reference/evidence.md#e11)

그 뒤의 격리 기하 시험 (`tmptest`) 자료에는 실패를 수리한 과정이 남아 있습니다. 회전된 대본의 글자 진행 방향을 정규화한 뒤 원래 좌표로 돌아오게 했고, OCR 상자 겹침을 실제 잉크 교차와 구별했습니다. 떨어진 표 선 때문에 제작진 글자 크기 그룹이 갈리는 문제와 옅은 이웃 행이 이름 상자에 섞이는 문제도 고쳤습니다. 이미 읽은 판독 결정을 회귀 자료로 고정했기 때문에, 좌표 수정 때 이름을 처음부터 다시 찾을 필요가 없었습니다.

새 3회차·17쪽 시험의 네 번째 실행은 1문서 완료·2문서 보류였습니다. 한 쪽짜리 회차에서 두 인물의 신원 문맥이 부족했습니다. 그래서 **처리할 페이지 집합**과 **신원을 확인할 참조 범위**를 분리했습니다. 이미 발견한 두 이름에 한정해 다른 회차 OCR을 해시·문서 연결이 있는 참조 사본으로 읽되, 그 참조 회차를 마스킹 큐에 추가하지 않았습니다. 작업 회차에서 보지 못한 학적 정보는 현재 관측인 것처럼 쓰지 않고 신원 근거에만 남겼습니다.

다섯 번째 검증에서는 기존 두 표본이 통과해도 새 기하 사례가 실패했습니다. 추가 수정 뒤 여섯 번째 회귀검증을 통과했고, 일곱 번째 실행은 같은 판독을 재사용해 17쪽 모두 완료했습니다. verified 11 / no_changes 6, 스태프 이름 삭제와 토큰 35/35였습니다. 이후 코드 8개·fixture 3개·문서 3개를 운영 패키지에 반영했습니다. 테스트 DB·신규 토큰·완료 상태는 운영 데이터에 합치지 않았습니다. 이곳에서는 실제로 제한된 에이전트 시험과 코드 수리의 반복이 있었고, 다른 운영 구간까지 같은 역할 구조가 유지된 것은 아닙니다. [E27](../reference/evidence.md#e27)

## 단일 에이전트 판독 대체본 (read-v2): 단일 에이전트로 바꾸어도 기하 실패는 남았습니다

9월 7일 사용자는 여러 의미 판단 에이전트를 버리고 단일 에이전트의 분석→수정→시험→피드백을 원했습니다. 당시 보류 분석에는 `NAME_TOUCHES_PROTECTED_FORM`, `NAME_RANGE_NOT_LOCATED`, `NAME_INK_CROSSES_PROTECTED_FORM` 같은 기계 원인이 많았습니다. 에이전트를 하나로 줄이는 일과 이 오류를 해결하는 일은 서로 달랐습니다.

`read-v2`는 텍스트 결정, 원본 준비, 좌표, 렌더, 사람 검수, 지정 피드백의 여섯 단계로 만들어졌습니다. 기존 5,330문서·66,010쪽과 316개 신원 binding을 승계하고, 피드백이 생기면 현재 출력의 검토를 다시 요구하도록 했습니다. 제작 당시의 29개 시험·기존 이미지 6개 호환 검증 뒤에는 **실제 실행**이 있었습니다. 첫 한 쪽의 이름 연결은 제출됐으나 좌표 단계가 `NAME_RANGE_NOT_LOCATED`와 `VISION_FAILED: nilError`로 막혀 새 이미지가 생기지 않았습니다.

사용자는 이어서 “1단계만” 진행하는 구조를 요청했습니다. 준비·좌표·렌더를 호출하지 않는 텍스트 전용 프롬프트가 만들어졌고, 두 packet에서 추가 5문서·84쪽의 판독을 제출했습니다. 보관 ZIP의 DB는 신규 `read` 85쪽, 기존 판독 승계 4,009쪽, 미판독 61,916쪽, 제출 packet 3개·열린 packet 1개, 신규 이미지 0개를 남깁니다. [E28](../reference/evidence.md#e28)

## 주 처리에서 바꾼 단위: 편성을 소유하는 것과 편성을 읽는 것

주 처리의 `program-claim`은 이미 같은 연도·학기·편성 전체의 소유권을 부여했습니다. 그러나 `program-packet`은 기본 최대 두 회차·45,000자, 최대 열 회차로 나누어 반환했습니다. 소유권이 편성 단위라는 사실만으로 실제 판단도 편성 전체 문맥을 사용한다고 볼 수 없었습니다.

9월 8일의 변경은 미제출 회차 전체를 하나의 packet과 결정문으로 받는 것이었습니다. 회차가 빠지거나 인용·문맥 검증이 틀리면 전체 제출을 거부하고, 중단할 때는 실제 끝까지 읽은 회차만 사유와 함께 남겨 같은 임대에서 재개했습니다. 긴 편성은 파일을 구간별로 읽었지만, 의미 판단과 제출은 편성 단위를 유지했습니다. 실제 47문서·320쪽 제출 사례에는 89 verified·185 no_changes·46 partial이 남습니다. 전체 편성 판독이 기하 실패를 지워 주지는 않았고, 대신 그 실패에 앞선 문맥 판단을 보존했습니다. [E13](../reference/evidence.md#e13)

이 시기 사용자가 명시한 최적화 대상은 에이전트와 사용자의 전체 작업 시간이었습니다. 같은 근거의 신원을 반복 판단하지 않고, 좌표 실패는 좌표로 보내며, 충분한 근거가 모이면 결론을 멈추고, 집계·재개 위치는 코드가 생성하도록 했습니다. 읽기 표시의 반복 JSON을 줄여 한 표본은 123,095자에서 35,815자가 됐습니다. 현재 OCR 줄·대안·식별 연결은 유지됐습니다. 앞선 310초 관측과 같은 병목을 가리키지만, 해당 수치 하나가 이 지시를 직접 유발했다고 기록되어 있지는 않습니다.

## 세션 입력 대체본 (read-next): 편성 단위 변경 이후 갈라진 세션 인터페이스

`read-next`는 이 개선된 이름 판독·마스킹 주 처리 (`read-only-masking`)에서 76,237개 파일과 운영 상태를 복사했습니다. 전체 편성 판독, compact 표시, 기존 geometry/render는 이미 원본에 있었고, 새로 더한 것은 `session-open/read/commit/close`와 첫 검토 인계였습니다. 하나의 의미 판단에 실제 등장 위치들을 묶고 예외를 따로 적으면 패키지가 공식 결정 형식을 조립했습니다. 전달 cursor와 실제 판독 선언도 분리했습니다.

이 패키지도 제작으로 끝나지 않았습니다. 9월 9일 한 편성 7문서·82쪽·3,651 OCR unit을 읽고 제출했습니다. 현재 session과 DB를 함께 대조하면 64쪽 변경 없음, 11쪽 verified, 7쪽 partial이며 출력 파일은 verified와 partial을 합쳐 18개입니다. 사용자가 보류하도록 한 연필 이름과 기하 검토가 남아 program은 `running`, 당시 close 결과는 `review`였습니다. 생성 스크립트를 쓰지 말라는 요청에도 제출 JSON을 Python으로 조립한 실행상의 이탈도 memory에 남아 있습니다. 인터페이스가 생겼다고 사용 습관까지 즉시 바뀐 것은 아니었습니다. [E29](../reference/evidence.md#e29)

제작 시점의 README와 STOP_POINT에는 여전히 “생산 미시작”이 적혀 있습니다. 그 문장보다 늦은 제출과 실제 출력이 이번 정정의 근거입니다. 또한 read-next가 나중 주 처리로 역이관됐다는 기록은 없습니다. 따라서 `read-v2 → read-next → 주 처리 편성 단위`라는 단선 계보를 만들지 않습니다.

## main/reverse: 공용 신원을 유지한 두 독립 실행 세션

주 처리에서는 한 세션이 한 편성의 문맥·신원·예외를 책임지고, 코드가 연도와 편성을 배정했습니다. main은 앞 연도부터, reverse는 뒤 연도부터 진행했지만 DB·고정 명단·기존 ID·토큰은 공용이었습니다. 당시 명단 181명 중 102명이 여러 연도에 나타나 독립 복제본에서 신원 권위를 따로 만드는 위험이 있었습니다. Vision 1개·렌더러 2개·내보내기 처리기 1개는 두 세션이 공유했습니다. [소유권 코드](../../../history/historical/names/session_ownership.py)

9월 9일의 20분 관측은 새 제출량과 이전 판독의 이월량을 구분했습니다. reverse의 233쪽 중 이미 읽은 64쪽을 빼 169쪽으로 계산하고, 읽었으나 제출하지 않은 35쪽도 제외했습니다. 이 측정은 실제 운영에서 어디까지 결과가 전달됐는지를 재는 방식이었습니다. 연도별 글자 밀도와 반복 인물 문맥도 달랐습니다.

최종 1차 DB에는 5,330문서의 공식 결정이 있고, 페이지 상태는 verified 21,009 / no_changes 40,714 / partial 4,182 / hold 105입니다. 제출 코드가 남긴 것은 결정과 근거, 상태와 다음 처리 위치였습니다. 과거 helper가 `review=read` 기본값을 채운 흔적까지 함께 남아 있어, 그 필드만으로 실제 판독 과정을 대신할 수 없었습니다. 후속 작업은 이미 얻은 신원·좌표·영수증을 재사용하면서 남은 4,287쪽을 원인별로 다뤘습니다. [E12](../reference/evidence.md#e12)
